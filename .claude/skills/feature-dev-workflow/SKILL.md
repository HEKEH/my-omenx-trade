# Feature Dev Workflow · 需求到落地全流程

把一份需求（产品文档 + 评审记录 + UI 设计稿 + 接口文档）系统地做成代码：**分析对齐 → 开发文档 → 开发路线图 → 分步开发 → 逐步自查+提交**。

> **可选依赖（非必需）**：本 skill 的部分环节借鉴并可联动 `superpowers` 插件里的方法论 skill（`writing-plans` / `verification-before-completion` / `subagent-driven-development` / `requesting-code-review` / `finishing-a-development-branch` 等）。**关键规则已内联在本文，未装也能完整运行**。

## 核心铁律（贯穿全程，务必遵守）

1. **绝不臆测**：遇到任何拿不准的点（需求歧义、字段映射不明、接口顺序/含义不确定、设计与接口对不上、交互边界不清），**绝不猜一个就继续**。但「绝不臆测」**≠ 事事反射式问人**：**先尽量用证据消歧**——查接口 schema 有无自描述字段、样例/测试环境数据、仓库既有约定；证据能定就**落盘后继续**；**证据定不了才问用户**，且**攒成一条**、给出推荐默认值 + 风险，让用户一次拍板。期间与该疑点**无关**的部分照常开发；相关代码写成**防御式**（显式常量 + `TODO`），绝不让「猜的值」静默进生产。
2. **文档先行、双关口校验**：开发文档、路线图都必须先产出、再让用户校验通过，才进入下一步（小/中等规模按 §0 缩放）。用户提问题就改，循环到用户明确说没问题。
3. **每步自查后才提交**：每个开发步骤完成后先自查代码（问题/遗漏立即处理），过项目的验收检查（类型检查 0 错误 + lint 通过，以项目实际配置为准）后，**把路线图对应任务打钩、再 git commit**（代码 + 勾选同一提交；无路线图的小改动直接提交）。
4. **遵循项目既有规范**：动手前先摸清目标项目的组件规范、目录约定、主题/配色体系、i18n 方式；项目里已有配套 skill（组件规范、移动端适配、i18n 等）时优先使用。
5. **可断点续跑**：本流程可能跨多次会话。重新触发时若已存在开发文档/路线图，**先读它们**，从**第一个未打钩任务**续做，不要重头再来。上下文被压缩后同样：先重读这些文件恢复状态再动手（见 §7）。
6. **验证靠证据**：声称某步「通过 / 完成」前，必须在**当前这一轮**真实跑过验收命令并读过输出（0 错误 / 通过）才能下结论或提交；禁止凭「应该没问题」推断。
7. **范围以路线图为界**：每个里程碑列出的「涉及文件」就是该步的改动范围。计划外的改动要么回路线图补上并说明，要么不做——不顺手扩大范围。

## §0 交互方式约定与进度跟踪

- **收集输入（§1）· 先选后填**：先用 `AskUserQuestion` **多选卡片**让用户勾选「会提供哪些材料」（选项最多 4 个），再按所选 + 必填项拼一段**聊天填空模板**让用户一次贴回。自由文本（路径 / 链接 / 需求名）走聊天模板，不逼用户点卡片「Other」。
- **开发中的临时提问 / 疑问对齐**：开放问答，用对话式直接问。
- **两处文档校验关口**（开发文档、路线图）：用 `AskUserQuestion` 弹卡片，选项固定为「通过 ✅」「有问题（我来说）」；选「有问题」则让用户描述，改完再弹，循环到「通过」。
- **离散是非/选择决策**（如是否用 Mock、目标项目确认）也用 `AskUserQuestion` 卡片。
- **流程按规模缩放**：

  | 规模     | 判据                                                                  | 文档关口                               |
  | -------- | --------------------------------------------------------------------- | -------------------------------------- |
  | 小改动   | 只改已有文件、≤2 个业务文件，不新增路由/接口/公共组件/依赖            | 不写文档，口头确认范围后直接做         |
  | 中等     | 已有页面/组件 3–5 个文件，无新公共边界                                | 开发文档与路线图合并一份（存为 `_开发路线图.md`，前半写开发参考章节），校验一次 |
  | 标准     | 新页面 / 新路由 / 新接口 / 新公共组件 / 批量 i18n / 埋点 / 跨模块     | 两份文档、两道校验                     |
  | 高风险   | 公共包、中间件、鉴权·支付·下单·资金等                                 | 两份文档、两道校验 + 独立 Verifier 复查 |

  宁可升级不可降级；判级要看真实受影响的路径，不能只凭需求文本里出现某些词。小/中等规模只省文档，**验收与自查一律保留**。

- **处理用户对文档的反馈时**：先完整理解每条反馈、不清楚就先问清再改；技术上不认同就摆事实沟通，不要表演式「你说得对」。
- **进度清单**：进入流程后，把下面这份清单放进回复并随进展打钩：

```text
Feature Dev Workflow 进度:
- [ ] ① 收集输入（目标项目 / 文档 / Figma / 需求名）
- [ ] ② 需求分析 + 疑问对齐（需求点↔设计↔接口）
- [ ] ③ 开发文档 → 用户校验通过
- [ ] ④ 开发路线图 → 一致性自检 → 用户校验通过
- [ ] ⑤ 按路线图分步开发（每步：开发→自查→验收→打钩→commit）
- [ ] ⑥ 收尾（全量验收 + 汇总 + 后续选项）
```

## §1 步骤一 · 收集输入

要收集的项：

| 项                   | 是否必填 | 可多个 | 说明                                                        |
| -------------------- | -------- | ------ | ----------------------------------------------------------- |
| **目标项目/模块**    | 必填     | 否     | monorepo 下的 app/包名，或单仓库的模块目录                  |
| **产品文档**         | 必填     | 是     | 本地路径（PRD/需求说明）                                    |
| **产品评审记录**     | 选填     | 是     | 本地路径                                                    |
| **UI 设计稿**        | 选填     | 是     | Figma 链接，可多个，逐一用 figma MCP 读取                   |
| **UI 评审记录**      | 选填     | 是     | 本地路径                                                    |
| **接口文档**         | 选填     | 是     | 本地路径，如 `openapi.yaml`                                 |
| **冒烟用例文件**     | 选填     | 是     | QA 的冒烟/回归用例清单；给了就意味着这轮要补对应的自动化用例 |

**第 1 步 · 卡片选材料**：`AskUserQuestion` 弹 multiSelect 卡片「这次会提供哪些材料？」，选项：`产品评审记录` / `UI 设计稿(Figma)` / `UI 评审记录` / `接口文档`（产品文档必填、不在此列；卡片最多 4 个选项，冒烟用例放到第 2 步模板里）。

**第 2 步 · 按所选给模板**：把必填项 + 勾选项 + 冒烟用例拼成填空模板，让用户一次贴回。例如勾了「Figma + 接口文档」：

```text
目标项目/模块:
需求名（选填，留空则从产品文档自动获取）:
产品文档路径（必填，多份用换行或逗号）:
UI 设计稿 Figma 链接（可多个）:
接口文档（如 openapi.yaml）:
冒烟用例文件（选填；给了这轮就要补自动化用例）:
补充:
```

- 需求名留空 → 读完产品文档后拟一个再确认。
- 收齐后逐一读取；同一项多值全部收下。
- 给了冒烟用例但目标项目没有对应测试基建时，问用户要不要引入——引入测试框架是另一件事，不顺手做。

### Figma（若提供了 UI 设计稿）

- **用 figma MCP 读取每一个设计稿链接**（`get_design_context` / `get_screenshot` / `get_metadata` / `get_variable_defs` 等），多个链接逐一读，不要只读第一个。
- figma MCP 疑似不可用时先**实际调用一次**核实：可能只是未授权/未连接。未授权 → 引导用户去授权；没装 → 提示安装。不要退回到抓网页 HTML 或凭截图猜。
- 涉及 UI 的需求，顺手确认一次 chrome-devtools MCP 是否可用（§5 像素对齐会用到），缺就现在提醒用户装。

## §2 步骤二 · 需求分析与对齐

读完全部文档 + 结合**当前代码**（Read/Grep/Glob 摸清现有结构、可复用的组件/hook/service/类型），做以下分析：

1. **拆需求点**：把 PRD/评审记录里的功能需求拆成明确的需求点清单。
2. **关联三方**：把每个**需求点 ↔ 设计图（Figma 节点/区块）↔ 接口（path/schema 字段）**对应起来，形成字段映射。
3. **摸底现有代码**：找出可复用项、需新增项、与现状的冲突点。

> 疑问按铁律 1 处理：先用证据消歧，定不了再一次性列清问用户。关联表不单独成文，直接作为开发文档的「字段映射」章节。

### Mock 数据决策（接口未就绪时）

没给接口文档、或接口未部署/未定稿都算未就绪；拿不准就问用户能否联调。

- **接口未就绪 → `AskUserQuestion` 问**：「本次是否用 Mock 数据先行开发？」（是 ✅ / 否）。
- **选「是」**：
  - **开发文档**加「Mock 方案」一节：mock 数据位置、**开关常量**（如 `<FEATURE>_USE_MOCK`，默认 `false`，本地调试改 `true`）、service/hook 按开关二选一、真接口后置到联调期。
  - **路线图**：靠前加「Mock 数据先行」里程碑；末尾加「真接口联调」里程碑（关开关、核对真实结构与 mock 差异、回归、边界收口）。
  - 项目里已有 mock 开关/助手模式就沿用，不另造轮子。
- **选「否」**：直接对真接口开发。

## §3 步骤三 · 编写开发文档

结合分析结果 + 当前代码，写一份**开发文档（开发参考）**。存放位置沿用项目已有的文档约定；没有约定时默认：

```text
<目标项目>/.doc/<需求名>/<需求名>_开发参考.md
```

**格式**：项目里已有同类开发文档就参照其风格；否则用骨架模板 [references/dev-doc-template.md](references/dev-doc-template.md)。建议章节：

- 用途 / 基线（复用了哪些已有模块）
- 功能定位与入口
- 分区（或模块）总览表
- **需求覆盖表**（`| 需求点 | 设计节点 | 接口 | 里程碑 |`）：每个需求点一行、四列填满，用来人工核对「有没有需求点漏做」。
- **证据表**（凡涉及判断都用它，一行一个可独立验证的断言）：

  | ID   | 断言                     | 证据                     | 影响         | 状态     |
  | ---- | ------------------------ | ------------------------ | ------------ | -------- |
  | E-01 | 某列表顺序由接口决定     | `service/x/index.ts:142` | 决定渲染顺序 | verified |
  | E-02 | 空态设计稿未画           | Figma `node-id=…` 无该节点 | 需产品确认 | blocked  |

  三条规则：**推断必须显式标注**，不能与事实混排；**截图只证明外观**，不证明组件身份或行为；**文件名只证明存在**，不证明这条代码路径是活的。

- **各分区数据与字段映射**（承载 §2 的关联表——开发文档核心）
- 接口清单（path / 入参 / 返回 schema / 对应 hook）
- 类型定义指引
- 交互与跳转约定
- 风险与待定项

写完 → 把文档路径告诉用户让其审阅，再用 `AskUserQuestion` 弹校验卡片（通过 ✅ / 有问题），循环到通过。

## §4 步骤四 · 编写开发路线图

用户确认开发文档后，写**开发路线图**，与开发文档放在同一目录：

```text
<目标项目>/.doc/<需求名>/<需求名>_开发路线图.md
```

**格式**：参照骨架模板 [references/roadmap-template.md](references/roadmap-template.md)。结构要点：

- **0. 原则与约束**：组件低耦合 / 复用基线 / 遵循项目规范；若决定用 Mock，写入「Mock 先行、真接口后置」原则。
- **1. 里程碑总览表**：`里程碑 | 名称 | 优先级 | 主要产出 | 依赖`（M0、M1…）。
- **2. 里程碑明细**：每个里程碑写「目标 + `- [ ]` 任务清单 + 涉及文件 + 验收标准」，字段/接口/布局只**引用开发文档章节号**，不重复实现细节。涉及文件列出新增/修改/删除的路径，以及涉及的路由、i18n key、埋点、依赖（逼自己把横切关注点想清楚，也方便评审核对）。
- **3. 依赖关系简图**（ASCII）。
- **4. 风险与阻塞表**。
- **5. 建议执行顺序**。

> **任务质量标准**（`writing-plans`）：每个 `- [ ]` 任务要**可执行、带确切文件路径、引用开发文档章节号**；禁止占位空话（「处理好边界」「加错误处理」「完善交互」）。粒度以「一个 commit 更合理」为准。验收口径写「✅ 类型检查 0 错误 / lint 通过」+ 可观察的功能点。
>
> **要写测试的里程碑**：把测试写进任务本身，顺序是「先写测试覆盖 A/B/C 情形（应为红）→ 再实现让它绿」，验收口径加「✅ test 通过」；要跑 e2e 的里程碑在验收口径里写明跑哪几个用例文件。
>
> **UI 密集需求**：除各组件步内做像素对齐外，在末尾加一个「视觉还原 / 走查」里程碑（整体尺寸/节奏、响应式、设计走查签收）。

**写完后做「跨制品一致性自检」**，再交用户校验：

- 开发文档里的每个需求点都有里程碑任务覆盖（需求覆盖表的「里程碑」列都指向真实存在的里程碑）。
- 路线图无自相矛盾 / 重复 / 悬空依赖；依赖顺序成立。
- 任务引用的开发文档章节号真实存在。
- 发现缺口先补正（或回补开发文档并告知用户），再进入校验。

自检通过 → 告知路径 → `AskUserQuestion` 弹校验卡片，循环到通过。

## §5 步骤五 · 按路线图分步开发

用户确认路线图后，按里程碑/任务顺序逐步开发，用任务跟踪工具（如 `TodoWrite`，若可用）跟踪进度。

> **「一步」= 路线图里一个 `- [ ]` 任务**，或一组放在一个 commit 更合理的相邻小任务。续跑时从第一个未打钩任务开始。

**连续执行**：步骤之间不要反复问「要继续吗」、不刷进度小结。只在下列情形停：① 被阻塞（缺依赖、命令反复失败）；② 遇到真正拿不准的歧义（铁律 1）；③ 全部完成。

每个步骤走同一个循环：

1. **开发当前步骤**：严格按开发文档的字段映射/接口/布局；能复用就复用。本步要写测试的话**先测后码**（先跑到红，再实现到绿）。
2. **自查 + 复查**：通读本步所有改动（漏字段、错接口、空态/边界、交互不全、与设计不符），有问题立即处理。**较大 / 高风险步骤**另派一个独立 Verifier（review 子代理）做「规范符合性 + 代码质量」复查。
   - **涉及组件 / UI**：做一轮像素级对齐——逐项核对间距 / 尺寸 / 字号字重 / 行高 / 圆角 / 颜色 / 状态，颜色走项目主题变量、不硬编码。逐节点精修可留到末尾「视觉还原 / 走查」里程碑，但本步至少不留明显偏差。见下「像素对齐」。
3. **验收**：本轮真实跑类型检查 + lint，读输出确认，不通过就修到通过（铁律 6）。命令以目标项目实际配置为准——先查 `package.json` / `tsconfig.json` / lint 配置，别想当然。
   - 用户坚持「别跑了直接提交」：可以照办，但如实标注「代码已提交，本轮未验收」，不打钩、不称「完成」。
4. **打钩**：把路线图里对应任务改成 `- [x]`。
5. **提交**：`git add` 本步代码 + 路线图勾选（同一 commit），在当前分支提交；commit message 语言与风格沿用仓库既有习惯。有 pre-commit hook 时，被 hook 自动格式化的改动一并纳入；hook 报错就修完重试，**不用 `--no-verify` 绕过**。

> **开发文档是活文档**：开发中发现文档与现实不符（接口字段变了、约束冲突、设计与实现对不上），立即回写开发文档；若涉及已与用户约定的行为，先确认。每个里程碑结束时核对一次「文档 ↔ 代码」是否一致。
>
> **用户中途改需求**：区分明确指令（「改为」「增加」「按这个执行」）与讨论（「可以考虑」）。明确指令先回写开发文档与路线图（补任务、补涉及文件），结构性变化（新目录/公共模块）要重新让用户校验路线图。

### 像素对齐：用浏览器实测渲染结果

涉及 UI 时，figma MCP 回答「设计稿是什么」，**chrome-devtools MCP 回答「浏览器实际渲染成了什么」**。只读自己写的样式代码去反推渲染结果，等于没验过。

1. `navigate_page` 打开本地 dev 的目标页（注意项目对 dev 端口/环境变量的要求）。
2. `resize_page` / `emulate` 切到设计稿对应断点（设计稿有几个端就量几个，如 PC 与移动端各量一次）。
3. **`evaluate_script` 读 `getComputedStyle` 拿真实 px**，逐项和 Figma 的值对：

   ```js
   const el = document.querySelector('[data-testid="xxx"]');
   const s = getComputedStyle(el);
   return { h: s.height, pt: s.paddingTop, fs: s.fontSize, fw: s.fontWeight, lh: s.lineHeight };
   ```

4. `take_screenshot` 与 Figma 截图并置，比对整体节奏。
5. `hover` / `click` 验 hover / active / 选中态——截图证明不了状态。
6. `list_console_messages` 确认没有运行时报错。

截图只证明外观，数值断言必须来自 `getComputedStyle`；反过来数值全对但整体不像，说明量错了节点。chrome-devtools MCP 不可用时提醒用户安装（`claude mcp add chrome-devtools -- npx chrome-devtools-mcp@latest`）；装上之前如实说明「未在浏览器实测」，不要宣称已对齐。纯 service / 逻辑类需求不需要这一步。

### 测试用例：不一定每次都写；要写就先写（红 → 绿）

**什么时候写**（任一成立）：

1. 高风险规模的改动（项目没有测试基建时，先与用户确认是否引入，不要随便找条命令充数）。
2. 目标项目已有测试基建，且本步改的是有判断的逻辑：纯函数、数据转换、状态机、边界与精度、金额、权限判定、错误分支。
3. 用户给了冒烟用例文件且项目有对应的 e2e 基建——清单里每条都要有用例接住。
4. 用户明确要求。

**什么时候不写**：

- 目标没有测试基建——现造一套是另一件事，先问用户。
- 纯展示型 UI / 样式对齐——靠像素对齐与视觉走查，e2e 也别去断言像素。

**红 → 绿纪律**：先写测试、真的跑一次确认是红的，再写实现跑到绿。**不许先写实现再补测试然后声称走过红**——一个从没红过的测试证明不了任何东西（断言写错、没跑到那行、被测逻辑被 mock 掉，都会永远绿）。

**回归用例改用突变验证**：回归用例保护的是已有行为，写完就是绿的。做法：备份源文件 → 故意改坏被测的那一处行为 → 跑用例必须变红 → 从备份还原 → 再跑回绿。只改一处；还原后 `git diff` 应回到改动前的状态；**别用 `git checkout <文件>` 还原**（会冲掉其他未提交改动）。

**e2e 分步窄跑、收尾全量**：用例按需求分文件（如 `e2e/<feature>.spec.ts`），分步时只跑本需求的文件；**收尾必须跑一次全量**——被这次改动弄坏的很可能是别的需求的用例。别依赖按 import 依赖选用例的机制（如 Playwright `--only-changed`）：e2e 用例走 URL 导航、不 import 业务代码，改了页面它可能一条都选不中。

### 可选：并行里程碑（worktree 隔离）

路线图中相互独立、可并行的里程碑，可用「协调者 + 隔离执行 + 顺序合并」加速：

- 每个并行里程碑派一个子代理，在独立 git worktree 里干活（`Agent` 工具的 `isolation: worktree`）。
- 主线只做协调；每个 worktree 内仍走完整单步循环。
- **合并顺序做**：一次合一个、解决冲突再合下一个。
- 有依赖的里程碑不并行；拿不准就串行。
- 并行期注意 `git commit` 提交的是整个索引：`add` 完立刻 `commit`，不用 `-a`。

## §6 步骤六 · 收尾

1. **全量验收**：再跑一次类型检查 + lint（本轮真跑）；有 e2e 的话跑全量。
2. **确认打钩齐全**：路线图所有任务 `- [x]`；未完成项如实说明。
3. **汇总**：改动清单、各项验收的结果、未完成任务、需求覆盖表里仍有缺口的需求点、本轮未验收就提交的次数（如有），如实告诉用户。
4. **给后续选项**：留在当前分支 / 发起 PR / 继续其他里程碑。**不擅自 push 或建 PR，等用户定**；开发完成本身不授权任何一项。

---

## §7 长任务抗压缩（上下文管理）

核心原则：**关键状态放文件，不放对话**。

1. **单一事实来源 = 路线图勾选 + 开发文档 + git 提交**。不确定进度时先重读路线图、开发文档与 `git log --oneline`。
2. **对齐结论即时落盘**：用户每回答一个疑问，立刻写进开发文档的「风险与待定项 → 已对齐结论」或对应字段映射处。口头澄清是压缩后最先消失的信息。
3. **每步提交即检查点**。
4. **用子代理隔离实现细节**：单步实现、大文件通读交给子代理，主线只保留路线图状态 + 关键决策。
5. **里程碑边界留续跑锚点**：在路线图顶部更新 `▶ 当前：Mx 完成；下一步：My 任务 Z；未决：…`。
6. **别反复通读大文档**：PRD / openapi 在 §2 读一次、提炼进开发文档，之后引用章节。
7. **警惕上下文焦虑**：临近上限时不要赶工——先 commit + 更新锚点 + 落盘未记录结论，再干净续跑。

### 常见 agent 失败模式 → 对策

| 失败模式                             | 对策                                                   |
| ------------------------------------ | ------------------------------------------------------ |
| 没验证就宣称完成                     | 铁律 6：本轮真跑验收命令并读输出                       |
| 测试后补（先实现再补必绿的测试）     | 先写测试跑到红再实现                                   |
| 恒真断言（回归用例写错也一直绿）     | 突变验证：故意改坏被测行为，确认用例变红               |
| 凭代码宣称已对齐                     | chrome-devtools 读 computed style；截图只证明外观      |
| 上下文满了赶工                       | §7-7：先 checkpoint，再干净续跑                        |
| 一把梭、改动无据                     | 小粒度任务 + 引用文档章节号 + 每步提交                 |
| 范围蔓延                             | 只做当前任务；新需求回 §2 对齐、进路线图               |
| 错误累积                             | 每步自查 + Verifier 复查，问题当步修掉                 |
| 上下文丢失                           | 三样落盘物 + 对齐结论即时落盘 + 续跑锚点               |
| 文档与代码脱节                       | 活文档：发现不符即回写 + 里程碑边界核对                |
| 文档校验后又改了                     | 行为层面的改动重新弹校验卡，事实性更正告知用户即可     |

## 全流程速览

```text
①收集输入(先选后填; 含可选的冒烟用例)
  → ②需求分析+对齐(先证据消歧, 定不了再问; 接口未就绪→问是否用Mock)
  → ③写开发文档(含需求覆盖表+证据表+字段映射) → 告知路径 → 弹卡校验 →(循环)→ 通过
  → ④写开发路线图(每里程碑: 任务+涉及文件+验收) → 一致性自检 → 弹卡校验 →(循环)→ 通过
  → ⑤按路线图分步开发(连续执行, 不反复问):
       每步 = [要写测试则先红后绿; 回归用例用突变验证] → 开发
             → 自查+复查(大步骤派独立 Verifier; UI 步用 figma + chrome-devtools 对齐)
             → 跑类型检查+lint(+test/e2e 窄跑) → 打钩 → git commit(代码+勾选同一提交)
  → ⑥收尾: 全量验收 + 汇总 + 后续选项(PR/合并/继续, 等用户定)
```
