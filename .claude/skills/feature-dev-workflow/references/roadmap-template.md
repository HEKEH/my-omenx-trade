# 开发路线图骨架模板

> 通用骨架。
>
> **任务质量标准（来自 writing-plans）**：每个 `- [ ]` 任务必须**可执行、带确切文件路径、引用开发文档章节号**；禁止「处理好边界」「加错误处理」这类占位空话——写清改哪个文件、做什么、怎么验收。粒度以「一个 commit 更合理」为准。
>
> **每个里程碑列出「涉及文件」**：新增 / 修改 / 删除的文件路径，以及涉及的路由、i18n key、埋点事件、依赖包（不涉及写 `-`）。它是该里程碑的改动范围，也方便评审核对横切关注点。里程碑编号统一用 `M<数字>`。

````markdown
# <需求名> — 开发路线图

> **配套文档**：实现细节见 [<需求名>\_开发参考](./<需求名>_开发参考.md)（下称「开发参考」）。本文件只排期与拆解，**不重复实现细节**，凡涉及字段/接口/布局均引用开发参考章节号。
> **整理日期**：<YYYY-MM-DD>
>
> **▶ 续跑锚点**（每完成一个里程碑就更新此行）：当前 <未开始 / Mx 完成>；下一步 <My 任务 Z>；未决 <…>。
````

## 写完之后

- **对照开发参考的需求覆盖表**逐行检查：每个需求点都有里程碑接住，引用的里程碑都真实存在。有缺口先补，再交用户校验。
- **要写测试的里程碑**：把测试写进任务本身，顺序是「先写测试跑到红 → 再实现让它绿」，测试文件列进「涉及文件」，验收口径加「✅ test 通过」。
- **要跑 e2e 的里程碑**：验收口径写明跑哪几个用例文件（如 `✅ e2e 通过（e2e/<feature>.spec.ts）`），分步只跑这几个，全量留到收尾。回归用例没有「先红」那一步，改用突变验证。
